# خطة IDPS: البداية بالبيانات الحالية والتعلم لاحقًا

## الواقع الحالي
- 36 شهرًا من بيانات 2021–2023 لـ6 منتجات، خام الشرارة/الحمادة، مستهدفات، وقود وفاقد.
- البيانات مصنفة **PROVISIONAL** إلى حين مراجعة مهندس العمليات والنسخ السنوية.
- تحاليل خام الشرارة والحمادة **ثابتة تاريخية** وليست سجلات إنتاج شهري مستقلة.
- ملفات 2024 و2025 المقدمة تتضمن إجماليات سنوية/تراكمية وتقارير شهر محدد؛ لا نلصقها باعتبارها أشهرًا مجهولة.

## ماذا نُفّذ الآن؟
1. اختبار استيراد وتحليل 36 شهرًا متصلة مع رفض التكرار والفجوات.
2. تدريب نماذج Ridge وRandom Forest وXGBoost منفصلة لكل منتج.
3. مقارنة بـ Last-month / Trailing-3-months / Seasonal Naive.
4. اختيار النموذج اعتمادًا على سنة 2022 وحدها، ثم اختبار الاختيار على سنة 2023 دون اختيار بأثر رجعي من 2023.
5. تدريب ملفات نماذج تجريبية على جميع الأشهر للبحث **فقط**، لا للاستخدام التشغيلي.
6. اختبار منفصل يمنع تسرب بيانات الشهر المستهدف إلى مدخلاته.
7. بوابة staging للأشهر الواردة حديثًا، ثم أمر retrain-approved لا يعمل إلا على تصدير معتمد.

## مسار التعلم المستقبلي — السجلات الجديدة

Production team → Daily Entry in Laravel/MySQL → Validation → Department Approval → Month Close → Monthly Approved Snapshot → AI Training Job → Validation & Holdout → Candidate Model Version → Review → Activate/Reject.

- البيانات **اليومية الجديدة لا تتحول تلقائيًا إلى تاريخ يومي قديم**. حتى يصبح النموذج اليومي مؤهلاً، تقيّم كمية وتنوع السلسلة اليومية بحد ذاتها.
- في البداية نستفيد من البيانات اليومية الجديدة بتجميعها إلى شهر كامل (وفق تعريفات القياس) وتدريب نموذج التنبؤ الشهري مجددًا.
- لا ندرب على بيانات غير مكتملة أو لم تغلق فترتها.
- لا نعدل نسخة النموذج الجاري بسبب سجل واحد؛ يُشغّل Retraining ضمن Job مجدول مع اختبار وموافقة.
- مقارنة الأداء يجب أن تراعي أن نموذجًا جديدًا قد يخسر أمام Baseline بسيط؛ لا تدّعي التحسن تلقائيًا.

## Workflow MySQL + Laravel المقترح
1. `source_files`: الملف الأصلي ومصدره وتاريخ تقديمه وhash.
2. `monthly_observations` (مقترح SQL مرفق): حقائق شهرية متتبعة المصدر والمراجعات.
3. `dataset_snapshots`: Snapshot للحظات التدريب مع checksum.
4. `training_runs`: نسخ التدريب والتحقق ومقاييس الأداء.
5. `model_versions`: النماذج وحالتها وartifact URI.
6. `forecast_runs` و`forecast_points`: توقعات الإنتاج ونوع المحرك.
7. `forecast_actual_evaluations`: المقارنة بعد ورود Actual معتمد.

عند إدخال يوم جديد، يُحفظ في MySQL. عند إغلاق شهر واعتماده، Job ينشئ Snapshot موحدًا قابلًا للتدريب؛ ثم يستدعي Python Trainer بشكل معزول؛ ثم يحفظ النتائج في MySQL. تفعيل النموذج يتطلب صلاحية وموافقة بشرية.

## الحد الأدنى لواجهة AI Training Studio
- رفع Dataset؛ فحص وMapping للأعمدة.
- استعراض Errors وWarnings وReview status.
- اختيار Target product وHorizon `next_month`.
- تنفيذ تجربة تدريب وعرض المقارنة بمصادر البيانات.
- سجل النماذج وحالتها: research / candidate / active / rejected.
- إعادة تدريب البيانات المعتمدة؛ مع صمام أمان يمنع التفعيل التلقائي.

## تشغيل التجربة

```bash
python -m pip install -r requirements.txt
pytest -q
python cli.py train
```

النتائج في `results/research_report.json` و`results/holdout_2023_predictions.csv`. ملفات الـ`.joblib` هي نماذج محلية **غير معتمدة**؛ لا تُحمّل إلا من مصدر موثوق.

لتجربة قبول بيانات جديدة (بعد الحصول على الشهر 2024-01 مثلًا، دون اختلاقها):
```bash
python cli.py stage --new /path/to/2024-01.csv
```
لن يُدمج الشهر تلقائيًا ولن يبدأ التدريب إلى أن يتم اعتماده عبر النظام. إذا بدأ الإدخال الجديد في 2026 مع غياب شهور 2024–2025، نقبل البيانات الجديدة في staging ونشير للفجوة، ولا نخلق أشهرًا وهمية. مسار retrain الحالي يدعم المقاطع المنفصلة دون اختلاق قيم، لكنه يستبعد أي شهر لا يسبقه 3 أشهر متصلة؛ ولا يستخدم Seasonal-12 عند وجود فجوة. النجاح العملي يتطلب تحققًا هندسيًا من تغيّر ظروف التشغيل والفجوة الزمنية. عند اكتمال تصدير كل الأشهر المعتمدة:
```bash
python cli.py retrain-approved --dataset /secure/exports/approved_monthly_history.csv
```
`review_status=approved` يجب أن يكون ناتجًا عن اعتماد محكوم بالصلاحيات داخل Laravel. الأمر المحلي لا يثبت هوية المراجع؛ يجب تنفيذ الربط الآمن قبل تشغيل Production.

## أول 4 دفعات تطوير
1. Foundation: MySQL migrations، مصدر البيانات، RBAC وAudit، اعتماد الشهور.
2. Analytics: عرض 2021–2023، Actual vs Target، 3 KPIs، reconciliation.
3. AI Studio: Data import + Quality + Training + Model Registry + Prediction API.
4. Continuous improvement: Daily Entry → monthly closure → snapshot → retrain candidate → evaluate → approved activation.

## نقاط تقيّد الدقة
- 36 شهرًا فقط → عدد محدود، لا يوجد ضمان قوة النموذج.
- ميزات التدريب الحالية كلها من تاريخ سابق؛ هذا يحمي من تسرب المستقبل لكنه لا يعطي معرفة مسبقة بالتوقفات غير المخطط لها.
- Forecast بعد Shutdown يتطلب معلومات الحدث وETA وسيناريوهات هندسية معتمدة؛ هذه ليست جزءًا من Dataset الشهرية وحدها.
- XGBoost ليس Online Learning تلقائيًا؛ التحسن يتم بإعادة تدريب نسخة جديدة على تاريخ معتمد، مع مراقبة النتائج.
- أي أرقام من 2024/2025 لا تُلحق بالأشهر الـ36 إلا إذا عُرفت الشهرية الفعلية وتعريفاتها وتواريخها بدقة.
